# 数据层修复：缓存新鲜度与预测日期轴

> 记录一次真实的数据事故：模型和评估代码都没错，结论也没错，
> 但**数据层的缓存策略把一个交易日的行情永久遮蔽了**，而没有任何报错。
> 这类 bug 最危险的地方在于它完全静默——不抛异常、不告警，只是让你看到旧数据。

## 1. 现象

2026-11-03 检查线上看板时发现：四只标的的预测锚点停在 **2026-10-30（周五）**，
而当天已经是 11-03（周二），11-02（周一）已收盘，数据本应可得。

排查分两步：

1. **数据源是否拿不到 11-02？** 用一个全新的缓存键（`end=20261103`）实测，
   四只标的都正常返回 `2026-11-02` 的 K 线 → **数据源没问题**。
2. **那为什么预测用的是旧数据？** 看缓存文件：

   ```
   600519_20231029_20261102_qfq.csv  →  最后一行日期: 2026-10-30
   ```

   文件名里的 `end` 是 `20261102`，但内容只到 `10-30`。

## 2. 根因

`scripts/data_utils.py` 的 `get_price()` 旧逻辑：

```python
if path.exists():
    return pd.read_csv(path)   # 只要文件在就返回，不校验内容到哪天
```

**缓存键里带 `end` ≠ 缓存内容真的覆盖到 `end`。**

事故链条：

| 时间 | 动作 | 结果 |
|---|---|---|
| 11-02 08:33 | 盘前跑一次预测，`end=20261102` | A 股未开盘，数据源只给到 10-30；这份"不完整"数据被写成 `*_20261102_qfq.csv` |
| 11-02 16:19 | 收盘后重跑，`end` 仍是 `20261102` | 命中早上那份缓存 → 直接返回 10-30 的数据 |
| 之后 | 每次重跑 | 每次都命中同一份旧缓存，**11-02 永久丢失** |

注意 10-31 是周六、11-01 是周日，都不是交易日。所以看起来"只差一天"，
实际是**丢了一个完整的交易日**，且锚点错位会让"预测起点"落在错误的日期上。

## 3. 修复

核心问题：**判断缓存能不能用，必须看内容，不能看文件名。**

新增的三个概念：

### 3.1 `_required_last_date(end)` —— 到底应该要求到哪一天

不能简单要求"最后一行 == end"，因为：

- `end` 可能根本不是交易日（周末 / 法定节假日）；
- `end` 可能指向今天，而今天还没收盘，数据源此时**给不出**当天 bar。

于是按真实交易日历推导：

```
required = end 之前（含）的最后一个交易日
若 required > 最近一个「数据已可得」的交易日：
    required = 最近一个「数据已可得」的交易日
```

其中"数据已可得"的口径是：该交易日**已过 15:40**（A 股 15:00 收盘，
日线数据在数据源落库还要一段时间，取 15:40 作为安全分界）。

这样：

| `end` | 当前时刻 | 要求缓存覆盖到 |
|---|---|---|
| 20261102（周一） | 11-03 13:22（周二，未收盘） | 2026-11-02 |
| 20261103（今天） | 11-03 13:22（未收盘） | 2026-11-02 ← 不苛求当天 |
| 20261103（今天） | 11-03 15:50（已收盘） | 2026-11-03 |
| 20261031（周六） | 任意 | 2026-10-30 |
| 20261001（国庆） | 任意 | 2026-09-30 |

### 3.2 `_cache_is_fresh(path, df, required)`

命中条件有且只有两条：

1. 缓存最后一行 ≥ `required` → 数据够新；
2. 未覆盖，但**元数据**显示"今天已为同一个 `required` 抓过" → 数据源当日
   确实到此为止（如停牌），不再反复联网。

### 3.3 `.meta.json` 旁挂元数据

每个缓存 CSV 旁边写一个同名 `.meta.json`：

```json
{
  "fetched_at": "2026-11-03T13:24:10",
  "rows": 729,
  "last_date": "2026-11-02",
  "required_last_date": "2026-11-02",
  "source": "auto"
}
```

为什么需要它：如果某只标的长年停牌，`last_date` 永远到不了 `required`，
只看新鲜度会导致**每次调用都重新联网**。记下"这个 required 我今天已经抓过了"，
就能区分「缓存陈旧」和「数据源确实没有」两种情况。

### 3.4 额外保护

- `refresh=True`：强制忽略缓存重新抓取（手动兜底）；
- **新数据比缓存更旧时保留原缓存**：数据源抖动 / 接口临时降级时，
  重抓可能返回更短的历史，直接写回会把好数据覆盖掉；
- **返回空表时沿用旧缓存**，不写空文件；
- `get_index()` 同样接入上述校验（指数缓存原本也只看文件存在性）。

## 4. 顺带修复：预测日期轴混入元旦

同一轮验证里发现：重跑后的 60 日预测轴包含 **`2027-01-01`（元旦，A 股休市）**。

根因在 `next_trade_days()`：它依赖的交易日历来自新浪，**只公布到当年年底**
（本次为 `2026-12-31`）。从 11-02 起只剩 43 个交易日，不足 60，于是整段退化为
`pd.bdate_range`——`bdate_range` 只剔除周末，**不认识中国法定节假日**。

修复：覆盖范围内用真实日历，覆盖外的部分用工作日近似并**剔除元旦**，
同时明确打印告警（不静默降级）：

```
⚠️ 交易日历仅覆盖到 2026-12-31，剩余 17 天按工作日近似
（已剔除元旦；其余法定休市以次年安排公布为准）
```

修复后：`2026-12-31（周四）` 直接跳到 `2027-01-04（周一）`。

> **遗留局限**：次年（2027）的完整休市安排要等官方公布后才有，届时需重跑。
> 春节等浮动假日无法用规则推算，因此跨年预测的末段只能视为近似——这一点已写进看板
> 「方法与局限」页，不做静默处理。

## 5. 第二个数据事故：盘中 K 线污染 qfq 复权基准

修完缓存新鲜度后重跑评估，发现 510300（沪深300ETF）的结果变了：同一批 cutoff、同一份
Kronos 缓存，`2025-12-29` 之后 20 日收益从 **−0.80%** 变成 **+1.83%**。

### 现象

`data/raw/` 下有 5 个 510300 缓存文件，两两对比重叠区间的收盘价：

| 文件 | 行数 | 末行 | 与其他文件最大相对差 |
|---|---|---|---|
| `..._20231029_20261102_qfq.csv` | 729 | 2026-11-02 | 0.000000% |
| `..._20240101_20261101_qfq.csv` | 683 | 2026-10-30 | 0.000000% |
| `..._20240516_20261102_qfq.csv` | 597 | 2026-10-30 | 0.000000% |
| `..._20240517_20261103_qfq.csv` | 597 | 2026-11-02 | 0.000000% |
| **`..._20231030_20261103_qfq.csv`** | **730** | **2026-11-03** | **9.296%** ← 异常 |

四个文件互相完全一致，只有最后一个不同，且**只有它多了一根 2026-11-03**。

### 根因

1. `load_ohlcv()` 把 `end` 设成 `pd.Timestamp.today()`，即「今天」；
2. 上一轮只修了「缓存命中判定」，**没修「实际传给数据源的 end」**——数据源照样返回当天 bar；
3. 那个文件生成于 **13:41**，A 股尚未收盘，拿到的是一根**盘中未完成的 K 线**；
4. **qfq 前复权以最新价为基准**，一根脏的最新价会让整段历史价格被重算——
   于是 2023-10 到 2026-11 的整个序列整体偏移，历史「未来收益」跟着全变。

510300 走的是东财 ETF 接口，该接口盘中会返回当天未完成 bar；同期股票接口没有返回，
所以只有 ETF 中招。这种「部分标的出错」最容易掩盖问题。

### 修复（两道防线）

```python
# 防线一：抓取终点收敛到 required（已完成的交易日），而不是调用方传的今天
fetch_end = pd.Timestamp(required).strftime("%Y%m%d")
df = fund_fetch(symbol, start, fetch_end, adjust)

# 防线二：数据源无视 end 硬返回当天 bar 时，落盘前一律截断
over = pd.to_datetime(df["日期"]) > pd.Timestamp(required)
if over.any():
    df = df.loc[~over].reset_index(drop=True)
```

### 验证

- 隔离脏文件后重抓：729 行、末行 2026-11-02，与同期其它文件相对差 **0.00000000%**；
- `2025-12-29` 起 20 日收益回到 **−0.80%**；
- 重跑评估，**全部指标回到修复前数值**（Kronos 终点 52.08% / IC +0.130 / CI [−0.173, +0.423]）；
- 新增 3 项回归测试，其中 `test_source_returning_intraday_bar_is_truncated`
  直接模拟「数据源硬返回今天 bar」的场景。

> **这条最容易漏**：上一轮修复只解决了「缓存会不会太旧」，没解决「缓存会不会太新」。
> 数据不是越新越好——**未完成的 bar 比过期数据更毒**：过期只是一天不准，
> 脏 bar 会让整段历史被重算。

## 6. 数据源一致性验证

重抓时东方财富被限流，自动回退到新浪。因为**不同数据源的复权因子算法可能不同**，
必须验证混用是否会破坏序列连续性：

| 检查项 | 结果 |
|---|---|
| 重叠区间（683 天）收盘价最大相对差 | **0.000000%** |
| 同日期成交量比值（新/旧） | **1.0000** |
| `amount / (close × volume)` | 0.9957（= 真实成交额，说明 volume 以「股」计） |
| 空值、单日涨跌 > 11% 的异常 bar | 0 / 0 |

结论：两个源在本项目使用口径下完全一致，回退是安全的。

> 这一步值得单独强调：**回退数据源之后如果不做一致性检查，就等于把
> 「混用不同复权基准」这个风险静默引入了**，而这种错误在图上很难看出来。

## 7. 回归测试

`tests/test_data_cache.py`（16 项，不依赖 torch / 不联网）：

- `_required_last_date` 的 6 个边界：周一 / 今天未收盘 / 今天已收盘 /
  周六 / 国庆 / 未来日期；
- `_cache_is_fresh` 的 4 种情形：覆盖达标命中、**陈旧必须不命中**（核心回归）、

- **盘中脏 bar 的 3 项**：抓取终点必须是 required（股票 / ETF 两条路径）、
  数据源硬返回今天 bar 时必须被截断（返回值与落盘缓存双重断言）。

## 9. 教训

1. **缓存必须校验内容，不能只校验存在性。** 尤其是"区间型"缓存——键里带了
   日期范围，不代表里面的数据真的覆盖了那个范围。
2. **盘前和盘后是两个不同的数据世界。** 同一个 `end` 在 08:33 和 16:19 拿到的
   东西不一样，缓存策略必须能感知这个差异（15:40 分界）。
3. **静默失败比报错危险。** 这个 bug 不抛异常、不打日志，只是让模型用旧数据
   继续跑，输出依然"看起来正常"。
4. **回退数据源后必须做一致性检查。** 否则复权口径混用会成为看不见的技术债。
5. **增量数据不等于只影响增量。** 前复权以最新价为基准，一笔新数据会重算整条历史；
   评估里用 `len(df)` 倒推样本位置，同样会让全部历史时点位移。

## 10. 第三个问题：cutoff 从数据末尾倒推，导致结果不可复现

### 现象

数据从 728 根变成 729 根（多了 11-02）之后，同样「12 个滚动时点」的**日期全部后移一个交易日**：

```
原 cutoff 首批: 2025-09-18, 2025-10-28, 2025-11-27, ...
新 cutoff 首批: 2025-09-19, 2025-10-29, 2025-11-28, ...
```

原因在 `rolling_cutoffs()`：

```python
idx = len(df) - (pred_len + 5) - i * gap   # 从数据末尾往回数
```

**只要追加一个交易日，所有历史 cutoff 就整体位移。** 后果有三个：

- 同一份代码今天跑和明天跑，样本完全不同 → **结果不可复现**；
- 48 个 Kronos 预测缓存（键含 cutoff 日期）全部失效 → 每次更新数据都要重新推理；
- 已写进文档 / 简历的数字，第二天就对不上。

### 修复

1. 默认改为**正向推进**：从最早可评估点（`lookback_min`）按 `gap` 往后走。
   新数据只在末尾追加时点，已有 cutoff 保持不变；
2. 新增 `--cutoffs` 参数，支持传**固定日期列表**做严格复现；
3. `--rollings` 从「取几个」改为「期望值」，实际取全部可评估时点
   （截断会重新引入漂移）。

```bash
# 严格复现某次评估的样本
python scripts/evaluate.py --symbols 600519,510300,601611,002600 \
  --pred-len 20 --samples 8 \
  --cutoffs 2025-09-18,2025-10-28,2025-11-27,2025-12-29,2026-01-30,2026-03-11,2026-04-13,2026-05-18,2026-06-17,2026-07-20,2026-08-19,2026-09-18
```

> 这类问题的共性：**「样本选择」一旦依赖数据长度，就等于依赖运行时间。**
> 评估脚本的样本必须由明确的日期规则决定，否则任何数据更新都会让历史结果失效——
> 而这个失效是静默的，跑出来的数字照样「看起来合理」。
